MAIZ Gestor de Contratos — v2

Evolução do PRD v1 (Junho 2026) depois de ~15 dias de uso real e de um benchmark direto contra o WebDox CLM. O v1 resolveu repositório, templates, aprovação, assinatura, SLA e prazos — e a maior parte já está construída e testada em produção. O v2 ataca o que ficou de fora: controle desde o primeiro pedido (não só depois que o contrato já existe), fornecedor como entidade central e governança de certidões — sem copiar o WebDox feature a feature, adaptando ao que a operação do grupo realmente precisa.

O que mudou de verdade: "Novo Contrato" deixa de ser o ponto de entrada. Todo contrato nasce como uma Solicitação — qualquer colaborador pode pedir, mas só vira Contract de verdade quando o Jurídico/Gestão de Contratos vincula um modelo. É a mesma motivação do WebDox ("impedir que qualquer um gere contrato sem triagem"), decidida depois de comparar com o processo real do grupo — não adotada por padrão.

Contexto do v2 — o que o v1 não cobria

🚦
Sem triagem no início
Hoje quem tem acesso cria contrato direto. Não há visibilidade do Jurídico sobre o que está por vir até o contrato já existir no sistema.
🏭
Fornecedor sem cadastro central
Fornecedor é só uma parte de um contrato — não dá pra ver histórico consolidado, nem vincular certidões a "este fornecedor" de forma consistente.
📜
Sem governança de certidões
CNDs e regularidades de fornecedores/parceiros não têm nenhum controle de validade ou renovação recorrente no sistema hoje.
🔗
Aditivo é gap real, não parcial
O PRD v1 já mencionava parent_id em contracts — conferido no código atual, esse campo não existe. Aditivo/renovação não tem suporte nenhum hoje.

Escopo do v2

Incluído no v2: Solicitação como ponto de entrada único · Arquétipos de fluxo por template (Fixo / Padronizado / Negociado) · Fornecedor como entidade central · Módulo de Certidões + lembretes periódicos por data · Chat simples por contrato · Versionamento de templates · Aditivos reais (parent_id, criados de dentro do contrato original) · Negociação simples com fornecedor (comentário/anexo de versão ajustada)

Fora do v2 (backlog futuro, decidido explicitamente): Importar histórico de envelopes do ClickSign/DocuSign · Notificação via Microsoft Teams (infraestrutura ainda não definida) · Integração com o sistema de Chamados interno (hoje em Power Apps, sendo reconstruído — integração via API fica pra quando ele estiver pronto) · Editor colaborativo com controle de alterações tipo Word (negociação com fornecedor fica simples por agora) · Construtor de fluxo visual (arquétipo fixo resolve os casos reais levantados)

PRD — v2

Funcionalidades Novas do v2

Sete módulos novos, decididos numa sessão de discovery comparando o processo real do grupo com o WebDox CLM — nenhum copiado 1:1, todos ajustados ao que foi confirmado como necessário.

1
Solicitação — Ponto de Entrada Único
v2 · Crítico

O "Novo Contrato" de hoje deixa de gerar um Contract direto — vira uma Request. Qualquer colaborador com acesso ao sistema pode abrir uma Solicitação, sem precisar saber qual template usar. O Jurídico/Gestão de Contratos vê a fila, vincula o modelo certo (ou pede mais informação, ou recusa), e só nesse momento a Solicitação vira um contrato de verdade. Resolve o problema real: hoje não há triagem — quem tem acesso de criação já gera o contrato sozinho, sem ninguém do jurídico saber que aquele processo existe até ele estar pronto.

Formulário idêntico ao "Novo Contrato" atual (sem fricção nova pro solicitante) Anexo de proposta/orçamento/minuta do fornecedor já na Solicitação Fila de triagem (aguardando vínculo de modelo) Vínculo de modelo + definição/override do arquétipo de fluxo no mesmo passo Conversão em Contract preserva o vínculo (request_id) Recusa com pedido de mais informação, sem virar contrato
2
Arquétipos de Fluxo por Template
v2

Em vez de um construtor de fluxo visual (WebDox tem um — decidido que não vale o custo de construção agora), cada template carrega um arquétipo que já define o comportamento esperado. Resolve a mesma necessidade (contratos diferentes precisam de tratamento diferente) com uma implementação muito mais simples.

A
Fixo / Padrão
Clientes (compra/venda, locação), Colaboradores PJ, Imobiliárias/Corretores. Só campos variáveis mudam, contraparte só assina, normalmente 1 nível de aprovação.
B
Padronizado c/ ajuste
Materiais, Equipamentos, Consultorias, Mão de obra. Ajuste pontual possível — usa o passo de negociação simples com fornecedor.
C
Negociado
Parcerias com proprietários de terra, Sócios/Cotas de SPE. Cláusulas mudam bastante, sempre Jurídico + Diretoria.
Campo flow_archetype no template (default) Override por Solicitação, só pelo Jurídico/Gestão de Contratos Arquétipo define: nível de trava de edição, se ativa o passo de negociação, alçada mínima
3
Fornecedor — Cadastro Central
v2

Hoje um fornecedor é só uma ContractParty de um contrato — nome e documento digitados de novo a cada vez, sem histórico central. Vira uma entidade própria, base pro módulo de certidões e pros filtros de repositório por fornecedor.

Cadastro único, reaproveitado entre contratos Histórico de todos os contratos com aquele fornecedor Base para certidões vinculadas Filtro do repositório por fornecedor
4
Certidões & Lembretes Periódicos
v2

Diferente do alerta de vencimento (sempre atrelado a um marco do próprio contrato), este é um lembrete que se repete numa cadência própria — ex.: CND renovada a cada 2 meses — independente de qualquer contrato estar vencendo. Vinculado a um Fornecedor e, opcionalmente, a contratos específicos.

Vínculo a Fornecedor (e opcionalmente a Contract) Recorrência configurável (ex.: a cada 2 meses) Upload do documento de certidão + validade Notificação a múltiplas pessoas, não só um responsável Status: válida · vencendo · vencida
5
Chat do Contrato
v2

Thread de texto simples vinculada ao contrato, visível a todos com acesso — registra a conversa que hoje acontece espalhada em e-mail e WhatsApp. Sem menção @, anexo dedicado ou notificação por comentário nesta versão (decidido explicitamente pra não duplicar o dossiê de documentos nem depender do sistema de notificações, que ainda está incompleto).

Comentário com autor + data/hora Visível pra quem tem acesso ao contrato Sem anexo (usa o dossiê de documentos já existente)
6
Versionamento de Templates
v2

Mantém o mecanismo atual (upload de .docx com {{campo}} extraído automaticamente) — decidido não trocar para merge fields nativos do Word, que exigiria reescrever o serviço de geração de documento sem ganho claro. A mudança é só passar a guardar histórico: hoje reenviar um .docx sobrescreve o template sem rastro de quem mudou o quê.

Cada novo upload cria uma versão, não sobrescreve Quem/quando de cada versão Contrato guarda qual versão do template foi usada na geração
7
Aditivos Reais
v2 · Crítico

O PRD v1 já previa isso (campo parent_id) mas nunca foi construído — conferido no código, o campo não existe. Diferente do WebDox (que vincula o aditivo ao original só no final da criação), aqui o fluxo começa de dentro da tela do contrato original: o botão "Criar aditivo" já nasce vinculado, sem risco de esquecer de linkar depois.

parent_id em contracts Criação sempre a partir da tela do contrato original Herda empresa/empreendimento/fornecedor do contrato pai Aparece no dossiê do contrato original como aditivo vinculado

SPECS — Arquitetura

Arquitetura

Esta seção reflete o stack real em produção hoje — não a aspiração do PRD v1 original, que previa React+Vite/SharePoint/MSAL e acabou implementado de forma diferente durante a construção. O v2 estende o mesmo stack, sem trocar nada de base.

Correção em relação ao PRD v1: o v1 especificava React+Vite, storage primário no SharePoint e login MSAL desde o MVP. Na prática, o time construiu com Next.js (não Vite), storage em Supabase Storage + disco local (SharePoint nunca foi usado como backend de arquivo), e autenticação via Dev Login (MSAL real ainda não integrado — depende de app registration Azure AD confirmado). Documentado aqui pra próxima sessão não presumir o v1 como fonte de verdade da arquitetura.

Frontend
Next.js (App Router) + TypeScript
React 19, Base UI, Tailwind CSS, recharts, lucide-react. Sem Vite — Next.js desde o início real da implementação.
Backend
Python + FastAPI
SQLAlchemy async + asyncpg, Alembic, Pydantic v2 — como previsto no v1, sem mudança.
Banco de Dados
PostgreSQL (Supabase)
Sem RLS nativo ativo hoje — isolamento por empresa é aplicado na camada de aplicação (filtro por company_id), não no Postgres.
Autenticação
Dev Login (hoje) → MSAL/Azure AD (próximo)
JWT HS256 auto-emitido pra qualquer pessoa do diretório sincronizado — único caminho de login hoje. Token RS256 real do Azure AD já é aceito pelo backend, só falta o fluxo MSAL no frontend + app registration confirmado.
Storage de Documentos
Supabase Storage (fallback: disco local)
Credenciais reais do Supabase Storage ainda pendentes — hoje tudo grava em backend/.data/storage/. SharePoint nunca foi usado como backend de arquivo, diferente do previsto no v1.
Assinatura Eletrônica
SignatureProvider · ClickSign API 3.0
Só ClickSign implementado e testado contra produção real. DocuSign continua como interface prevista (SignatureProvider), mas factory.py hoje só aceita clicksign — qualquer outro provider derruba com erro.
IA — Agentes
Claude API (Anthropic)
6 agentes reais chamando a API (não stub): Redator, Revisor Jurídico, Briefing de Aprovação, Gestor de Prazos, Extrator, Leitor de Marcos. Precisam de Redis/Celery rodando para disparar — indisponível no ambiente de dev atual, falham rápido de propósito.
Notificações
Celery + Redis (planejado) · Resend + Z-API (não configurado)
Worker ainda é TODO — sem credenciais Resend/Z-API no ambiente atual. Microsoft Teams como canal fica fora do v2 (sem infraestrutura definida ainda).

SPECS — Fluxos

Fluxos de Sistema — v2

Fluxo 1 — Da Solicitação ao Contrato

Colaborador preenche Solicitação (+ anexos)
→
Entra na fila de triagem
→
Jurídico/Gestão vincula modelo
→
Define ou confirma o arquétipo de fluxo
→
Solicitação convertida em Contract
→
Segue o fluxo normal (revisão → aprovação → assinatura)

Recusa: se a Solicitação estiver incompleta, o Jurídico recusa com um motivo — o solicitante é notificado e pode reabrir com mais informação. Nunca vira Contract nesse caminho.

Fluxo 2 — Negociação Simples com Fornecedor (arquétipo B)

Minuta enviada ao fornecedor (link com token, 72h)
→
Fornecedor comenta ou anexa versão ajustada
→
Jurídico revisa o ajuste manualmente
→
Aceita (atualiza minuta) ou recusa (mantém original)
→
Segue para assinatura

Fluxo 3 — Criação de Aditivo

Usuário está na tela do contrato original (vigente)
→
Clica "Criar aditivo" — já herda empresa/fornecedor/empreendimento
→
Novo Contract criado com parent_id preenchido
→
Segue o fluxo normal de aprovação/assinatura
→
Aparece no dossiê do contrato original como aditivo vinculado

Fluxo 4 — Lembrete Periódico de Certidão

Job diário verifica certidões
→
Calcula próxima renovação (issued_at + recurrence_months)
→
Dentro da janela de alerta?
→
Notifica todos em notify_user_ids
→
Certidão renovada → novo registro, ciclo reinicia
SPECS — Controle de Acesso

Controle de Acesso — v2

Os papéis (visualizador, aprovador, juridico, admin) não mudam. O v2 mapeia os conceitos "Operador" e "Colaborador" do WebDox sobre os papéis já existentes, sem criar um role novo.

Colaborador (WebDox) = visualizador (nosso) — ganha a permissão de criar Solicitação, mas não cria Contract direto. Operador (WebDox) = juridico + admin — quem pode triam Solicitações, vincular modelo e definir arquétipo de fluxo.
